- **Android project scaffolded 2026-10-22** in `android/` per architecture section 4: nine modules, pinned toolchain (Gradle 8.14.6, AGP 8.13.2, Kotlin 2.4.21, KSP 2.3.9, JDK 17). AndroidX core 1.18.0, lifecycle 2.10.0, navigation 2.9.8 and Compose BOM 2026.06.01 are the newest that compile against SDK 36; lazysodium-java stays at 5.1.4 because 5.2.0 needs Java 21. compileSdk 37 is the owner's call. Document versions at the end of 2026-10-26: FRD v0.18, BLE protocol v0.38, song format v0.12, GUI design v0.38 (D-01 to D-82), architecture v0.12, test plan v0.9, assessment v0.10 (SP-26); `bash scripts/check-design.sh` passed on them.
- **Reception on the phones is the design's main risk** (protocol Q2, Q3, NFR-PERF-01, FRD Q14 open): receivers hear 13–40 % of advertising events, about half with Wi-Fi on. The answer chosen by the owner: erasure coding (v0.21), GATT repair with a 5 s deadline from the group's start (v0.22 to v0.25), the 3 s fallback from an unheard extended set, the library as the fast path. Measured with v0.24: S23 median 4.6 s, Huawei 5.8 s, every song by repair (D-05 run 18). Simulated (`design/test-results/2026-10-25-S-01-06.md`): 25 singers about 3.8 s, 100 singers 5.9 s on the legacy carrier, 2.6 s with the extended set. Songs on the legacy carrier now travel mostly over GATT. Field tests decide.
- **Implementation state (2026-10-26):** `core/protocol` holds the wire layer (`cbor/`, `frame/`, `fec/`, `payload/`, `beacon/`), the carousel, the pure state machines, `engine/SingerEngine` and `engine/LeaderSession`, and the GATT service and client (`gatt/`); `core/testing` has `SimulatedAir` (calibrated to 600 ms per connection) and the conformance vectors for songs, archives and setlists; `platform/ble` advertises, scans and serves GATT (`AndroidGatt.kt`); `core/songformat` implements song-format sections 3 to 13 (song parser, library file and import, release archives on an own bounded ZIP reader, setlists). `platform/storage` installs a checked archive (`LibraryInstaller`: staging, a new directory per install, one Room transaction with songs, FTS4 search, setlists and report); its DAO has no instrumented test yet. `app/library/LibraryRepository` adds libraries from a file or a pasted URL (archive, `releases.json`, or a GitHub or GitLab repository) with the size before download, A013, L006 and the licence text. The app has the home screen (D-21), the *Bibliotheek* screen (D-50, D-51: list, add online or from a file, licence, report with a sentence per code, *Bijwerken* with what changed, *Aan* / *Uit*, remove; Room schema version 2, migrations automatic from version 1), the radio check, the two-phone test and the reception bar (D-81). The home screen's book icon opens the *Zangbundel* (the songbook, called *Liedboek* until guiDesign v0.27; D-52: search by title or lyrics, sort, chips, *Wis filters*; reading a song in the day theme, D-53), which reaches the *Bibliotheek* screen (guiDesign v0.16) and the *Setlists* screen (D-54: make, rename, duplicate, delete; editor with drag and swipe; songbook editing mode with checkboxes; D-53's button in the reading view; Room schema version 3; the entry point is mine, guiDesign v0.17, for the owner to confirm), with library setlists, `.zbs` import from a file or HTTPS address and export through the share sheet (D-59, SP-25). The default library (FR-LIB-02, FRD Q3 resolved 2026-10-26) is `github.com/pe1mew/Zangbundel-bibliotheek`, offered while not installed. Not yet (end of 2026-10-26): the automatic update check on Wi-Fi (FR-LIB-13), in gatherings one continuous scan from home into the gathering (Android and EMUI limit scan starts), statistics sharing and the badge in the leader drawer (D-61), the leader sheet's editing tabs (D-58), resume after a crash (D-67), fit-to-width (D-28), the toolbar and song-info sheet in the songbook's reading view (the singer's page has both since guiDesign v0.38); opening a `.zbs` shared from another app, the songbook's orders and filters by use, Request and the delegate Control commands (phase 2 since FRD v0.18; answered `0x81` and `0x89`), document 8, `stay` and State notifications, relays, LeaderMachine's lifecycle in `LeaderSession`, Jazzer fuzz targets (need JUnit 5).

- **Songs ahead (2026-10-26, FRD v0.16, BLE v0.32, guiDesign v0.28):** the leader sends every setlist song as document 9 from the start (`Carousel` rule 7, `LeaderSession.Publication.ahead`); singers keep them by `dh` and take them as document 3 when the signed manifest names that `dh` (`SingerEngine.takeAhead`); the setlist lists only `dh` per position. The reception grid shows itself while the current song is incomplete (setting kept in `AppSettings`). On the phones the state record still comes by repair 4–5 s after *Nu*, which is now the bottleneck; the S23 stayed on the extended carrier and collected little ahead (`design/test-results/2026-10-26-songs-ahead.md`). BLE v0.33 (carrier by rate, state repair after 1 s) took the S23 to 0.85–1.2 s from *Nu*; the Huawei at 13 % stays at 4.8–5.9 s, and only option B of `design/proposals/2026-10-26-state-after-push.md` (beacon names the current song) can get it under 2 s (`design/test-results/2026-10-26-state-after-push.md`). Per-frame timing showed why C did nothing there (the rate rule fires at 2.5 s first) and that every push costs each singer a setlist and an Info connection; next step proposed in `design/proposals/2026-10-26-burst-state-first.md` (state lead-in, judge after 1 s, no Info repair, setlist before song). Diagnostics events `StateFrame` and `RepairDecided` exist in `SingerEngine`. BLE v0.34 built (all four): Huawei 2.8–3.9 s, S23 1.2–2.4 s from *Nu*; costs: songs not held ahead come about 3 s later by air (so by GATT), and the setlist, which changes every push, is still repaired each push. BLE v0.35 (owner's idea): the setlist is the `dh` order alone and does not change on a push; the state carries `cpos` and `sung`; a late joiner shows earlier sung songs from its songs ahead (`SingerEngine.Event.EarlierSong`, `Gathering.earlier`). Huawei 2.6–2.7 s from *Nu*, no setlist repair; tested 2026-10-26. The A52's slow carousel (a burst pass 9–10 s) was the send loop waiting 100 ms after ~30 ms of work: 7.4 ticks/s; fixed to a fixed rate, 10.0/s measured (leader log `leader rate`). Since FRD v0.17 / guiDesign v0.30 the reception grid has no setting: hidden, long press on the singer's top line opens it, a tap closes it (`SingerSettings` remains only for the two-phone test).
