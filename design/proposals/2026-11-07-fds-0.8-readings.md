## 2. How it was checked (2026-11-07)

- **Row 1** has a permanent test, `PackageTest` "libsodium rejects a signature under the identity key, canonical or not". It runs `JvmSodiumCrypto`, the same `crypto_sign_verify_detached` the app's `SodiumCrypto` calls, on lazysodium-java's libsodium, with:
  - the identity key `AQAA…AAA=`;
  - the non-canonical key y = p + 1;
  - a signature R = identity, S = 0, against three messages;
  - a non-canonical R;
  - a genuine signature, as a control.

  All forgeries are rejected, and the genuine signature verifies. It has not been run on a phone: the app uses lazysodium-android's libsodium build.
- **Rows 3 to 9** were probed with a temporary test, since deleted, that ran `SongParser` and `PackageImport.parseManifest` on each example the manager gives.
- **Rows 2 and 8, refusal with VIEW-02:** this is from reading `PackageImport.view`, not from a run.
- **The library repository's `validate.py`** was tested by its session on 2026-11-07, and today it reads rows 3, 4 and 5 as the app does:
  - it accepts C1 characters;
  - it accepts `{c: a\}`;
  - it treats an NBSP-only line as blank, because Python's `strip()` removes more than spaces and tabs.

  It agrees on `{c: a} {new_song}`, `{album}` and W004. If this is approved, it follows the song format change through the new conformance vectors.

## 3. The differences

### 3.1 Set names (row 2)

**What the app does today:** `parseManifest` accepts a set name like `Demo}\n<libraryId>/x`, ` Demo`, `De{mo` or a name in NFD.

The app never writes a setlist from a set name, and it never shows the manifest's name. It installs the view's setlists, and `view()` compares each one's title with the set's name. A name that cannot be a title therefore fails that comparison, and the package is refused with VIEW-02. So no entry can be injected into the app. Only the code differs.

**Recommendation: the manager's reading.** `parseManifest` refuses such a name with MAN-02:
- a line break, `{` or `}`;
- leading or trailing space;
- a name that is not NFC.

The refusal then names the real fault, at the first rule. It also does not rely on the view comparison to stop an injection.

### 3.2 C1 control characters (row 3)

**What the app does today:** `SongParser` (S001), `Setlist` (SL001) and `PackageImport.validName` (PF-20) refuse U+0000 to U+001F (except LF, CR and tab) and U+007F. They accept U+0080 to U+009F.

**Why the app is wrong:** song format 5.1 says "control characters other than LF are not allowed", and Unicode counts U+0080 to U+009F as control characters (category Cc). These characters show as nothing or as boxes. U+0085 is also read as a line break by some tools, so a line can look different on the leader's phone than in the file.

**Recommendation: change the app** to refuse them in all three places. Song format 5.1, S001 and SL001 would name the ranges: U+0000 to U+001F except tab, LF and CR, and U+007F to U+009F. The library repository's `validate.py` would follow, with a conformance song vector.

This also affects release archives and snapshots: a song with a C1 character is skipped there (S001), where today it imports.

### 3.3 A directive ending in an escaped brace (row 4)

**What the app does today:**
- `{c: a} {new_song}` is S011, as the manager reads it.
- `{c: a\}` is read as a comment `a}`.

**Recommendation: the manager's reading.** Song format 5.2 asks that the last character is `}`, and that braces inside are escaped. An escaped `\}` at the end is a brace inside, so the directive has no closing brace. Song format 5.2 would say so, the app would report S011 (SNG-04), and a conformance vector would be added.

### 3.4 What counts as whitespace (row 5)

**What the app does today:**
- A line holding only U+FEFF or U+0085 is a lyric line, as the manager reads it.
- A line with a no-break space before a directive is S011, as the manager reads it.
- **A line holding only a no-break space (U+00A0) is blank.** Kotlin's `isBlank()` treats NBSP as whitespace.
- The canonical form already trims only spaces and tabs (`Canonical.kt`).

**Recommendation: spaces and tabs only, everywhere.** That means blank lines, directive lines and the trimming of names and values. Song format 5.1 and 5.2 would say so.

Why:
- It is one rule instead of several.
- It matches the canonical form, which the hash depends on.
- It does not depend on a language's idea of whitespace: Kotlin, Python and JavaScript each count different characters.

The app would replace `isBlank()` and `trim()` in the parsers with a check for spaces and tabs. `validate.py` would follow, and a conformance vector would be added.

### 3.5 VIEW-03 and `min_app_version` (row 8)

**What the app does today:** `view()` runs the format 1.1 checks (L002 to L006) with the app's own version. A view with `min_app_version` `0.2.0` passes L005 there, and is then refused with VIEW-02 for not saying `0.1.0`.

**Recommendation: the manager's reading.** VIEW-03 exists so that no older app refuses the view, and the oldest app is 0.1.0, the value PF-41 fixes. L005 is therefore checked as an app 0.1.0 would check it, and `0.2.0` is VIEW-03.

This changes one example in the approved proposal of 2026-11-06, O-11 (g): there, `min_app_version` `0.2.0` was given as a VIEW-02 case. The rest of that reading stands: a departure from PF-41 that passes L002 to L006 is VIEW-02.

  - 3.2, C1 characters in three checks;
  - 3.3, a closing `\}`;

- **Song format:** 5.1, 5.2, S001 and SL001, with a version bump. Conformance vectors for 3.2, 3.3 and 3.4.
- **The library repository:** `validate.py` and `release.py` for 3.2 to 3.4, through the conformance corpus.

## 5. The owner's decisions

**2026-11-07: "Approve all".** All five recommendations are taken as written.

What was done in this repository the same day:
- **3.1.** `parseManifest` refuses, with MAN-02, a set name that holds a brace, a line break or a control character, that has leading or trailing spaces, or that is not NFC.
- **3.2.** `SongParser.isControl` (C0 except tab, LF and CR; DEL; C1) is used in S001 and SL001. `validName` refuses C1 for PF-20.
- **3.3.** A directive whose closing brace is escaped is S011.
- **3.4.** Blank and directive lines are judged after trimming spaces and tabs only. So are directive names, values and the `meta` split, in songs and in setlists. An indented directive is now a directive. Before, it was S011.
- **3.5.** VIEW-03 runs the format 1.1 checks as app 0.1.0.
- **Song format v0.24:** 5.1, 5.2, 5.3, S001, SL001. Song vectors `control-c1`, `directive-escaped-close` and `directive-indented`.
- **Tests** in `PackageTest`: set names, a C1 name, VIEW-03 with `min_app_version` `0.2.0`, and an NBSP-only line.

**Left open, for the owner** (found while building, and not covered by this proposal):
- **The display text of song format 9.1** still trims trailing *whitespace*, in Kotlin's sense, which includes the no-break space. A line holding only an NBSP is therefore no longer blank, but it is also not a lyric line: it adds nothing to the line list.

  The manager's engine trims spaces and tabs only, so it lists such a line. Changing 9.1 would change the line list, whose positions the BLE protocol sends (`pos`). In a gathering of mixed app versions, such a song would then be numbered differently on different phones. This needs its own decision.
- **An indented comment** (`  # x`): the app reads it as a lyric line. The manager trims first and reads it as a comment. Song format 5.2 says "first character is `#`".
- **The manager trims names and values with JavaScript's `trim()`,** which also removes NBSP and U+FEFF. The app now trims spaces and tabs only. The manager would follow 5.3.
