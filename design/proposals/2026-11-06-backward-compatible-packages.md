# Proposal: library packages that older apps can read, and old formats in a new app

| Field | Value |
|---|---|
| Proposal | Every library package also carries a format 1.1 copy of itself (the *1.1 view*): `zangbundel.json`, a licence file, the songs under `songs/` and the sets as `.zbs` files, generated by the library manager and covered by the package's signature. An older app then imports a package as an ordinary snapshot, without its integrity features. The reservation of the UUID form for packages is withdrawn, so no existing library can become invalid. A new app reads every 1.1 library as before, with one small library-level warning that it is not signed. |
| Date | 2026-11-06 |
| Status | **Approved by the owner 2026-11-06, in full; answers in section 8.** Specified in song format v0.20 and the library manager's FDS draft 0.5. FRD (FR-LIB-05, FR-LIB-09), GUI design, assessment and test plan follow in the app session. |
| Asked by | The owner, 2026-11-06: "to make the new contract backwards compatible, what should be changed to the new specification? I want the old app to keep working but without the extra integrity features that a new app can use with the new format. If a new app reads an old format library it should work but only with a small warning." |
| Affects | `design/song-format.md` 4.2, 4.3, 11, 12.5, 12.11, 13.5; `design/functional-requirements.md` FR-LIB-08, FR-LIB-09; `design/guiDesign.md` (library screen, import report); `design/security-privacy-assessment.md` (SP-37 or a new finding); `design/test-plan.md` 3.2; the library manager's FDS (`Zangbundel-bibliotheek-manager/design/FDS.md`, draft 0.4): 3.2, PF-10, PF-12, STR-01, 4.1, MF-01, D-31, D-32, new view rules |
| Builds on | `design/proposals/2026-11-04-library-package-id-and-file-type.md` (approved 2026-11-04); this proposal would change two of its decisions, listed in section 7 |
| Requirements | FR-LIB-05, FR-LIB-07, FR-LIB-08, FR-LIB-09, FR-LIB-16, FR-LIB-17, FR-LIB-21, NFR-MAINT-01, FRD constraint 7 |

## 1. Recommendations at a glance

| Goal | Recommendation |
|---|---|
| An old app (format 1.1, such as 0.3.0) keeps working with packages | **A package is also a valid 1.1 snapshot.** The library manager writes a 1.1 view next to the manifest, in the same single library folder: `zangbundel.json`, `LICENSE`, the song folders under `songs/`, and one `.zbs` file per set. An old app finds `zangbundel.json` inside the single top-level folder and imports the file as a snapshot (song-format 12.5), which it already does today. It ignores `manifest.json` and `manifest.sig`. It gets the songs, sets and licence, but no signature, version number, title check or whole-or-nothing validation. |
| New apps keep the integrity features | **The view is listed in the manifest and checked against it.** The view files are entries of `files`, so the signature covers them. A new app reads the library from the manifest, as now, and refuses a package whose view disagrees with its manifest. A view altered to mislead old apps is caught by every new app. |
| Nothing that is valid today becomes invalid | **Withdraw the UUID reservation (L006).** A `zangbundel.json` id in the UUID form is accepted again. A package and its 1.1 view carry the same id, which is what makes them one library on every device. |
| A new app reads an old-format library with a small warning | **One library-level warning, W013 "not signed".** It is shown once in the import report and as a short note on the library screen, and it never blocks anything. Songs, setlists and Bluetooth work exactly as today. |
| Versions | **No major version.** The library format stays 1.1 and the package `formatVersion` stays 1. The view is new required content in packages, but the FDS is a draft and no packages exist yet. |

## 2. Why packages and 1.1 are not compatible today

| Point | Package (FDS draft 0.4) | What a 1.1 app needs | Effect today |
|---|---|---|---|
| Library file | `manifest.json` | `zangbundel.json` at the root or in the single top-level folder (12.5) | An old app refuses a package with A001, "no zangbundel.json at the archive root", which suggests a broken file rather than "update the app" |
| Song location | `<library folder>/<song id>/<song id>.cho` (PF-12) | `songs/**/*.cho` | Even with a `zangbundel.json`, an old app would find no songs (L008) |
| Licence | In the manifest only, no licence file (FDS D-31) | `license.file` must exist (L007) | Refused |
| Maintainer | Optional (FDS D-32) | Required: `name` and `email` or `url` (L002) | Refused when absent |
| Title | Up to 100 characters | `name` at most 80 (L002) | Refused when longer |
| Sets | Lists in the manifest | `setlists/*.zbs` | Sets lost |
| Library id | UUID, reserved for packages; a `zangbundel.json` id in that form is refused (L006) | Any id in id syntax | The reservation makes previously valid ids invalid: a breaking change under section 10.4, made without a version bump |
| Extra files | The library folder holds nothing else (PF-10, STR-01) | — | A package with a 1.1 view would fail STR-01 today |

## 3. The 1.1 view

### 3.1 Layout

```
<library folder>/
├── manifest.json            package: read by new apps
├── manifest.sig             package: only when signed
├── zangbundel.json          1.1 view, generated
├── LICENSE                  1.1 view, generated
├── songs/
│   └── <song id>/
│       └── <song id>.cho    shared by both
└── setlists/
    └── set-<n>.zbs          1.1 view, generated, one per manifest set
```

The song folders move under `songs/`. The folder per song stays, as the FDS keeps it for later attachments (PF-12). A 1.1 app reads `songs/**/*.cho` at any depth and only requires the file name to equal the song id, which a package already guarantees (PF-14).

### 3.2 How the library manager fills the view

On every save, the Editor writes the view from the manifest.

| 1.1 view | From the manifest | Note |
|---|---|---|
| `format`, `format_version` | Fixed: `zangbundel-library`, `1.1` | 1.1 is needed for the setlists |
| `id` | `libraryId`, unchanged | The same id in both views, so setlists, memories and Bluetooth references agree between old and new apps |
| `name` | `title` | The FDS limit on `title` goes down from 100 to 80 characters, the limit for `name` (L002) |
| `description` | `description`, or `title` when absent | 1.1 requires the field |
| `maintainer` | `maintainer` | Must be present: see section 7, point 2 |
| `license` | `id` and `summary`; `file` is `LICENSE` | `LICENSE` holds `license.text`, or `license.summary` when there is no text |
| `min_app_version` | Fixed: `0.1.0` | Every released app reads a 1.1 snapshot with setlists |
| `setlists/set-<n>.zbs` | `sets[n-1]`: `{title: <name>}`, `{meta: id set-<n>}`, then one entry `<libraryId>/<song id>` per song | The `set-<n>` ids are the ones a new app already gives manifest sets (song-format 13.5, approved 2026-11-04), so a set has one id on every device |

The view files are listed in `files` with their size and SHA-256 (MF-01), like the songs. A signed package therefore signs its view too.

### 3.3 New rules for the package (FDS section 6)

| Rule | Check | Severity |
|---|---|---|
| VIEW-01 | The view is present: `zangbundel.json`, the licence file it names, and one `set-<n>.zbs` per set. | Error |
| VIEW-02 | The view agrees with the manifest as section 3.2 says: id, name, description, maintainer, licence id, summary and text, and every set with its songs in order. | Error |
| VIEW-03 | `zangbundel.json` passes the 1.1 library checks (song-format 4.3), so an old app does not refuse it. | Error |

The Editor never fails these rules, because it writes the view itself. They protect against a view that was edited by hand, or tampered with to mislead old apps.

### 3.4 What each app does with a package

| | Old app (1.1) | New app |
|---|---|---|
| Recognises the file as | A snapshot (12.5), warning A102 | A package: `manifest.json` in the single top-level folder takes precedence (12.11, unchanged) |
| Reads | `zangbundel.json`, `songs/`, `setlists/`, `LICENSE` | `manifest.json`, the songs, the signature; checks the view against the manifest (VIEW-01 to 03) |
| Validation | Song by song: a bad song is skipped (FR-LIB-07 for snapshots) | Whole or not at all (APP-01) |
| Signature, version, title check, device memory | None | As in the FDS |
| Updates | A newer package is opened as a file and replaces the snapshot | As in the FDS decision table (8.3) |
| At the campfire | Same library id, same content hashes: mixed groups work | Same |

## 4. Old formats in a new app: the small warning

A new app reads release archives, snapshots and `zangbundel.json` libraries exactly as today. On import it adds one finding:

| Code | Level | Message (Dutch / English) | When |
|---|---|---|---|
| W013 | Warning, library-level | *Deze bibliotheek is niet ondertekend: de app kan niet laten zien wie hem gemaakt heeft of controleren dat er niets aan veranderd is.* / *This library is not signed: the app cannot show who made it or check that nothing was changed.* | Every import of a release archive, snapshot or `zangbundel.json` library |

The warning appears once in the import report. The library screen then shows a short *niet ondertekend* / *not signed* note where a signed package shows its fingerprint (FDS SG-21). It never blocks an import, a song, a setlist or a gathering, and the leader sees no other difference.

A release archive from `releases.json` is still checked against its published SHA-256 (12.7). The warning is about who made the library, not about damage in transit.

Section 7, point 4 asks whether an unsigned *package* gets the same warning.

## 5. Prototype

`design/proposals/2026-11-06-dual-package-prototype.py` builds a package with a 1.1 view as section 3 describes. It has one song from the conformance corpus, one set and a placeholder signature. The library repository's `scripts/release.py verify` applies the 1.1 import rules; according to the conformance corpus it agrees with the app on all 58 vectors. It accepts the package:

```
songs/vader-jacob/vader-jacob.cho: OK hash=750da7b1aa8ce93c624bdcdb0f172190 lines=2
setlists/set-1.zbs: OK hash=42b0829bb7a4ea1a6695cc6f67fd70ac entries=1
troop12.zbl WARNING A102 repository snapshot (single top-level directory, no manifest): revision unknown, no update checks
Archive accepted, 2 warning(s).
```

The second warning (W002) is the corpus song's missing recommended metadata. The setlist entry `<libraryId>/vader-jacob` resolves inside the library, so a UUID library id works in a 1.1 app as it is. The prototype does not exercise the new-app side (VIEW rules, signature); that needs the package code.

## 6. Documents and tests that change

### 6.1 This repository

- **`design/song-format.md`:**
  - 4.2 and L006: the UUID reservation is withdrawn. A UUID-form id is valid, and the 4.3 URL clash rule does not apply between a package and its own 1.1 view.
  - 11: new warning W013.
  - 12.5: a package's 1.1 view is a snapshot.
  - 12.11: rows for the view, the VIEW rules and what each app reads.
  - 13.5: the `set-<n>` ids are shared with the view.
- **`design/functional-requirements.md`:**
  - FR-LIB-08: packages carry a 1.1 view, so apps that read format 1.1 import them.
  - FR-LIB-09: the UUID reservation is removed.
- **`design/guiDesign.md`:** the *niet ondertekend* note on the library screen, and W013 in the import report.
- **`design/security-privacy-assessment.md`:** a finding on the view as a second copy of library data. The risk is a tampered view meant for old apps. Old apps have the protection of a snapshot today, which is none. New apps refuse a mismatch (VIEW-02).
- **`design/test-plan.md` 3.2, with conformance vectors:**
  - a package with a view, accepted as a snapshot by the 1.1 rules;
  - the same package as a package, by the new rules;
  - a view that disagrees with its manifest (refused by VIEW-02);
  - a `zangbundel.json` with a UUID-form id, accepted;
  - W013 on an old-format import.

### 6.2 The library manager's FDS

- **Layout and the files it may hold:** 3.2, PF-10 and STR-01 allow the view. PF-12 moves the song folders under `songs/`.
- **Manifest:**
  - 4.1: `title` at most 80 characters;
  - `maintainer` required, if point 2 is decided that way;
  - MF-01 lists the view files.
- **Validation:** rules VIEW-01 to VIEW-03.
- **Licence file:** D-31 says the library has no licence file. It now gets a generated one.
- **Editor:** the save steps (7.6) write the view.

### 6.3 The library repository

- No validator change for the reservation: `validate.py` never implemented it.
- `scripts/conformance.py` runs the new library vectors as soon as the pin moves to them.

## 7. Points for the owner

1. **Withdraw the UUID reservation** (reverses point 2 of the 2026-11-04 decision). Recommended: it is the one change that makes valid libraries invalid, and a package and its view need the same id. What the reservation guarded against was an id belonging to two different libraries. Here the package and its view are one library, and two different libraries choosing the same UUID by accident is not a realistic risk.
2. **Maintainer in packages** (FDS D-32 made it optional). Format 1.1 requires a maintainer with an e-mail address or URL, and the view must pass the 1.1 checks. Two options:
   - **(a) recommended:** make `maintainer` required in packages, so the Editor asks for it once per library;
   - **(b)** keep it optional, and have the Editor refuse to save without one. That amounts to the same thing with more words.

   A placeholder maintainer is not offered: it would tell old apps something untrue.
3. **A generated licence file** (FDS D-31 said there is none). Recommended: the manifest stays the source, and `LICENSE` is a derived copy for old apps, checked by VIEW-02.
4. **W013 also for unsigned packages?** Recommended: yes, with the same text. A package without `manifest.sig` proves no more about its maker than a release archive does.
5. **Title limit 100 → 80 characters.** Required by format 1.1, which refuses a longer `name`.
6. **Order of work:**
   - first this repository's specifications;
   - then the FDS change request;
   - then the conformance vectors together with the package code in the app;
   - the library manager writes the view from its first version.

## 8. The owner's decision (2026-11-06)

The design of sections 3 and 4 is approved. The answers to section 7:

| Point | Decision |
|---|---|
| 1. UUID reservation | Withdrawn. A `zangbundel.json` id in the UUID form is valid again (song format v0.20, 4.2, L006). |
| 2. Maintainer | Required in packages (option a): the Editor asks for it once per library (FDS draft 0.5, MAN-08). |
| 3. Licence file | A generated `LICENSE` in the 1.1 view, copied from the manifest and checked by VIEW-02. Asked a second time on 2026-11-06, because without a licence file every 1.1 app would refuse the view (L007). |
| 4. W013 for unsigned packages | Yes: the same warning and *not signed* note as for old formats. |
| 5. Title limit | 80 characters, the limit of `name` in format 1.1. |
| 6. Order of work | As proposed. This session wrote song format v0.20 and FDS draft 0.5. The app session takes the FRD (FR-LIB-05, FR-LIB-09), GUI design, assessment, test plan and the package code. |

The public-key format the app session asked about on 2026-11-06 is settled by FDS draft 0.5 too. Every rule already said raw: the field rule, the key file, SG-11 and SG-20. Only the example in 4.1 was an X.509 SubjectPublicKeyInfo (DER, 44 bytes). The draft states the raw form as SG-05 and corrects the example to the RFC 8032 test key (`11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=`, fingerprint `21FE-31DF-A154-A261`; wrapped, the same key would give `06E3-FD8F-DA29-BB60`).
