# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/). The project has no released version yet; the design documents carry their own document versions in their headers.

## [Unreleased]

### Fixed
- The system bar icons were dark on the night-blue background on phones in light mode (seen on a Samsung A52, Android 14). `MainActivity` now declares both bars dark, so the icons stay light; checked on the A52 and a Huawei Mate 20 Lite (Android 10).

### Added
- GATT registration and repair (ble-protocol 8–10): `core/protocol` `gatt/` (Data stream codec, `LeaderGattService` with the singer table, sealed Join, Transfer with clamped ranges and paced notifications, connection slots; `GattClient`), `engine/SingerEngine` that runs `SingerMachine` against a `Transport` and verifies what it collects, `engine/LeaderSession` (keys, Info, signed state, carousel and GATT behind one push); `SimulatedAir` with advertising loss and GATT slots in virtual time; the GATT server and client in `platform/ble` (`AndroidGatt.kt`); the two-phone test runs both. 166 protocol tests; in simulation a singer at 13 % reception gets each push in 3.3–5.5 s, twenty singers at 13–40 % in a median of 5.4 s. On the phones (D-05 run 17) every push reached the Huawei in a median of 5.5 s and the S23, which hears none of the A52's extended frames, in 9.0 s, all by repair. Request and the delegate commands of Control are not built (answered `0x81` and `0x89`); Control op 10, leave, is.
- Erasure coding in `core/protocol` (ble-protocol v0.21): `fec/ReedSolomon` (GF(2⁸), Cauchy coefficients, test vector shared with an independent Python computation), coded frames in the framer with the new layouts, a reassembler that decodes from any `k` distinct frames and asks repair only for what it still needs, a carousel that sends sources before repairs and cycles coded state frames, and the singer's rate-based repair rule. 140 protocol tests; at 40 % simulated reception the state and a 2 kB song arrive in a median of 13.3 s on three legacy sets and 2.7 s on the extended carrier. On the phones, with Wi-Fi on and about 13 % reception, all four pushes arrived in 38–40 s, where none had before (D-05 run 11). On the extended carrier, with a Galaxy S23 leading and the A52 listening, all five pushes arrived in a median of 5.8 s; with the A52 leading none did, because the A52 hardly transmits its extended set beside three legacy sets (D-05 runs 12 and 13). With only its beacon and extended set the A52 was still not heard (2 extended advertisements in 390 s, run 14); the two-phone test has a *Lead, extended set only* button for this. A probe (*Probe the extended set*, `AndroidTransport.extendedSecondaryPhy2M` and data-update counts) found no setting that puts the A52's extended set on the air: at most 33 of about 600 advertisements a minute reached the S23, none on the 1M PHY, while the A52's stack confirmed every update (D-05 run 15). The same probe sent by the S23 reached the A52 in every step, about 150–176 extended advertisements a minute, as often as the beacon (run 16).
- `design/proposals/2026-10-25-erasure-coding.md`: the change the owner chose for low reception, in detail for approval: a systematic Reed–Solomon code over GF(2⁸) with Cauchy coefficients across the frames of a document, on both carriers and for every broadcast document; new legacy (26 bytes) and extended (14-byte header) frame layouts carrying `k`, `idx` and `len`; redundancy `r = min(2k, 256 − k)`; passes of all `n` frames; decoding in the reassembler; GATT repair when a singer's own reception rate will not reach `k` within 10 s (legacy) or 4 s (extended); the library as the fast path. Simulated delivery of 2 kB: 12–31 s on legacy, 2–6 s on extended, against 61–170 s today.
- `AndroidTransport` advertising and scanning (`platform/ble`): the beacon set with the service UUID and the beacon as scan-response manufacturer data, legacy data sets opened until the stack refuses, the extended set on 2M where supported, frames replaced with `setAdvertisingData`, one continuous scan filtered on the service UUID and company `0xFFFF`. The `Transport` interface now speaks in the protocol's sets instead of raw advertising bytes. GATT is not written yet.
- Two-phone test screen in the `debug` and `fieldtest` builds (assessment v0.6, SP-24): one phone leads a test gathering with the real carousel and a synthetic document, the other listens and times each push. First run in `design/test-results/2026-10-25-D-05.md`: the beacon carries each push to the singer within about a second, but the Huawei received only 13–17 % of the A52's frames (and the A52 38 % of the Huawei's beacon), so no 2 kB document arrived complete by broadcast. Three follow-up runs ruled out the controller's scan filters, scan requests on scannable data sets and a cap on the total: the Huawei hears each advertiser about one time in six to ten, the A52 one time in three. `AndroidTransport` keeps both switches (`hardwareFilters`, `scannableDataSets`) as diagnostics. The PC's Bluetooth as a third receiver heard each of the A52's sets about as often as the Huawei's lone beacon, so the receivers, not the senders, set the rate: 17 %, 24 % and 38 % of the advertising events. With Wi-Fi off on both phones the Huawei heard about 40 % and 2 kB documents completed by broadcast, in 44 and 49 s against a 5 s target. The test screen no longer crashes when a phone refuses the beacon set.
- Beacon and join-link codecs in `core/protocol/beacon` (ble-protocol 6.1 to 6.3, 6.5): encoding A as manufacturer data, encoding B as the iOS local name with RFC 4648 Base32, names cut at character boundaries, frames and test signals never read as beacons; the join link in its HTTPS and `zangbundel://` forms with the same bounds as the published join page and the `SHA-256(pk)` check against `gid`. 131 protocol tests.
- Protocol state machines in `core/protocol/engine`, pure and driven by timed events: the singer (ble-protocol 3.3 with 10.2–10.4, 10.9, 10.11: discovery, registration only after a verified state, results 1 to 5 with background retries every 30–60 s, the repair timers of 7.6, random delays with the `BUSY` variant, backoff from 300 ms to 2 s with jitter, reconnecting after 10 s, ended after 5 minutes, leaving), the leader (10.1, 10.5, 10.9, 10.10: pre-start scan, random first `seq`, strictly increasing `ts`, one warning about another gathering, resume with `seq` + 1, 60 s of ending) and the connection-slot policy of 10.8. 119 protocol tests.
- Broadcast carousel scheduler in `core/protocol/carousel` (ble-protocol 7.4): Set S, the large-document sets with even and odd frames, the extended set, the three-pass burst shared over the legacy sets, the pass time `pt`. A simulated singer measures delivery of a pushed 2 kB song without loss: 4.7 s with three legacy sets, 7.0 s with two, 14.0 s with one, 1.1 s on the extended carrier. 90 protocol tests.
- Sealed payloads in `core/protocol` (ble-protocol 8.4): write framing, Join, Request and Control always sealed to `ek`, Transfer sealed exactly for document 8, the Join response and document 8 sealed to the singer's `xk`, `gid` binding, and refusals carrying the 8.3 error codes (`ProtocolError`). 77 protocol tests.
- Payloads of ble-protocol section 9 in `core/protocol/payload`: the signed state record (signing, and verification of the signature before the body is parsed, then `gid`; the `ts` rule), its manifest, Info, the song, setlist, message, request-status and request-list documents, and the Join, Request, Transfer and Control writes with their per-operation required keys. Known keys of the wrong type or size are refused, unknown keys ignored, texts truncated at character boundaries. Raw DEFLATE with an output cap that refuses a bomb while inflating, and the 10 % rule of 7.3. Tests run Ed25519 through lazysodium-java (test-only, in `core/testing`), pinned at 5.1.4 because 5.2.0 needs Java 21.
- The protocol's own CBOR codec in `core/protocol` (architecture A-08): preferred serialization on encode; on decode it rejects indefinite lengths, tags, floats and other simple values, duplicate map keys, nesting deeper than 8, invalid UTF-8, integers outside 64-bit signed range, trailing bytes and payloads over the caller's limit, and checks every length against the remaining input before allocating. Tested against the RFC 8949 vectors and 50,000 random inputs.
- Frame layer in `core/protocol` (ble-protocol 7.2, 7.5, 9.7): legacy and extended frame codec, a framer per carrier, and a reassembler with a bitmap per document version, at most two versions per document (the two seen most recently, since `dv` has no order: it is two bytes of the document hash, and `seq` for the state), merged repair ranges (at most 32), repaired bytes into the same buffer, and a bound of 64 KiB per document. 
- Radio check (test-plan F-01) in the `debug` and `fieldtest` builds: `AdvertisingProbe` in `platform/ble` counts the legacy advertising sets that open, times advertising-data updates, and finds the largest extended payload, per structure and spread over several; the results screen shares them as text. The release APK contains neither the screen nor the probe (checked). Security assessment v0.5 adds SP-23 for it.
